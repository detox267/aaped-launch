# Inactive Fusion deployment

`deploy-inactive-vps.cjs` is an operational helper for the reviewed **58ee233a0f5505f7cc62a976dea282c67c553eca** program binary. Adding this helper does not change that binary or the public source commit that must be verified. Its own download must also be pinned to a reviewed commit and SHA-256.

The program address is `CVzSF4nNHwu12giZUo9WZYGBw5VAbmgFN11ywVXizfmo`; the retained loader upgrade authority and deployment payer are `5zDozijrnBsdQ4CgDddJhBFDrmuoSya8C2EG15sZEFt6`. The pre-existing recovery buffer key derives `7spbodSrFFD9a67Sf5ej4UTkTcfhQzschwVfTxCR7wZF`. Keys stay in owner-only files on the VPS, outside Git. The helper creates no keys and never transfers funds to the operator or holders.

With only an absolute Fusion build directory argument, the helper is read-only. With `--deploy` followed by that directory, it spends mainnet SOL through the installed Solana CLI. It checks the exact release checkout and binary hash/security.txt, existing backend's disabled flags, all four local signer identities and permissions, mainnet genesis, unused program/config/buffer accounts, deployer ownership, fresh rent and sufficient balance. The program is allocated exactly 243,600 bytes, and a separate 0.5 SOL reserve is required beyond conservative peak rent. The reserve is headroom for fees and subsequent work, not another transfer or a guaranteed all-in testing price.

Deployment uses explicit payer, upgrade authority, program key and persistent buffer key. It sets a 10,000 micro-lamport/CU priority price and at most five signing attempts. Preflight and feature checks remain enabled; `--final` is never used. CLI stdout/stderr may include sensitive RPC details, so they go only to an owner-only private log. Public reports omit RPC URLs, key paths/contents, arbitrary exception messages and raw CLI errors.

Before invoking the CLI, the helper exclusively creates and fsyncs `deployment-attempt.json`. A second invocation cannot replace it or begin another unresolved attempt. An interrupted upload must be reconciled using the original program/buffer keys and the private log; do not delete the journal or automatically create a new buffer. If the program is already deployed, the helper verifies its actual finalized bytes and retained authority and exits without another deployment. Original attempt and receipt records are retained.

The first upload stopped with `Max retries exceeded`. Its finalized buffer is still controlled by the pinned admin and contains only reviewed binary bytes or unwritten zeros. After reconciling this specific failure, `--resume` enables one controlled retry using the same program, binary, RPC, authority and funded buffer. It requires the original record and failure log, no active CLI upload, finalized buffer history and matching confirmed/finalized accounts. Wrong buffer contents, authority or original release pins stop the command. Existing buffer rent is credited once in the balance requirement; a new buffer is never allocated. The retry uses 50,000 micro-lamports/CU and at most 20 signing attempts, with a separate exclusive `deployment-resume-1.json` record. A second uncertain resume requires further reconciliation; neither record is erased or silently incremented. All writes remain copies of the same reviewed bytes at the same offsets. This recovery mode does not change holder-payment journal rules or authorize re-signing uncertain payouts.

The public preflight includes an `rpcProvider` label inferred from the configured Fusion RPC hostname: `Helius`, `Alchemy`, `Solana public RPC`, or `other_or_proxy`. It never prints the hostname, URL or API key. Both the RPC checks and the actual CLI deployment use the backend configuration's `cfg.rpcUrl`; the Solana CLI's default endpoint is overridden explicitly. A custom proxy label cannot establish its upstream provider. The controlled resume rejects the known shared public mainnet endpoints before spending more fees, allowing a missing provider configuration to be corrected instead of silently repeating the upload there. It never substitutes another RPC or changes the environment file.

A successful CLI exit is insufficient: the helper checks the finalized loader-v3 program binding, actual bytecode and exact retained authority. It records a receipt only after these pass. The helper does **not** initialize the config, change Raydium authority, alter the API/PM2 configuration, publish source-verification metadata, start a worker, or enable launches/rewards. The absent config blocks application operations; initialization itself requires the retained loader authority and defaults to paused.

After deployment, independently check the on-chain accounts, then verify the program against the public **58ee233** release. Only after source verification should config be initialized paused and platform registration changed. Backend launch/purchase/payout integration, operator funding, pricing, eligibility/tier reconciliation and the capped canary remain separate activation prerequisites. Do not advertise the program as publicly verified or the platform as live merely because this deployment helper succeeded.

## Public source verification

`--verify /absolute/fusion/build/directory` verifies the existing deployed program; it does not deploy or upgrade it. It rechecks its actual bytes, loader authority, mainnet identity and local signers, then invokes checksum-pinned `solana-verify 0.5.2`. The CLI clones and rebuilds public commit **58ee233**, using `fusion`, `moonz_fusion` and SBPF architecture `v0`, before uploading verification metadata. This upload spends network fees and metadata account rent. The explicit upload signer is the existing Fusion admin. A private temporary CLI configuration binds that same signer and the current backend RPC for both verifier commands, avoiding the verifier's default-wallet lookup without modifying global Solana configuration. The temporary config is removed on normal completion or handled errors; CLI logs remain private because the vendor CLI prints its RPC URL.

The helper requires a finalized verification PDA owned by `verifycLy8mB96wd9wqq3WDXQwM4oU6r42Th37Db9fC`, derived from `otter_verify`, the admin and the Fusion program. Its decoded program, signer, version, repository, full commit, exact build arguments and deployment slot must match. CLI exit success alone is insufficient. An exclusive `verification-upload-attempt.json` preserves the original upload attempt. If a matching PDA already exists, a repeated verification command can resume public verification without paying to upload metadata again; an uncertain upload with no matching PDA requires reconciliation.

After metadata is confirmed, `remote submit-job` requests the independent public rebuild. The helper checks the actual public status and both executable hashes, commit/repository, closed/frozen flags, and freshly re-read on-chain binary and authority before reporting `public_source_verified`. An accepted job, CLI exit code or local hash match does not count as public verification. The source-verification service receives public program/uploader addresses; RPC credentials stay in the private local configuration/logs. Status/report files contain no RPC URLs, API keys or key material. Application configuration is never initialized or enabled by this operation.
