# Five-minute collection engine

**RPC adapter and a restricted canary runner are implemented and locally tested; no VPS activation or mainnet deployment has been performed.** `collector.cjs` is the scheduling engine; `rpc-adapter.cjs` connects it to real RPC, quotes, signing and receipt verification. `run.cjs --check` is read-only and never loads a signer. `run.sh` can sign and broadcast only with an explicit private live config, verified deployment, retained authority and a nonempty list of up to ten canary mints. This is collection/sales only. Website launch and holder/platform payout integration are still release blockers; do not turn on the old worker for PDA tokens.

The schedule is fixed at 300 seconds, aligned to wall-clock boundaries (for example 12:00, 12:05, 12:10). A newly registered CA starts at the next boundary. Each due cycle snapshots withheld base-token tax, collects it in batches of at most 16 accounts, and waits for finalized receipts. The collected tokens accumulate in that CA's base vault until a capped sale into its configured paired asset clears **US$30**. Collection and sale are phases of the same cycle, not separate five-minute timers. Collection continues below the sale threshold; there is no trade-count trigger or holder-eligibility gate here.

Each proposed sale must have at least 30,000,000 USD micro-units of conservative quoted proceeds, after token/pool fees and the slippage allowance, **before** the 25% platform split. Value the actual paired output using its own trusted USD price; never assume a stablecoin or another pair token is worth $1. Both quote and price must be no more than 30 seconds old. Use decimal integer strings/BigInt, not floating-point dollars. This is an off-chain quote-time execution policy, not an on-chain USD guarantee or restriction on a separately operated signer. The on-chain minimum output is in paired-asset units.

A balance below US$30 stays in its own vault across cycles and restarts. Each capped chunk is checked independently; a smaller remainder also stays for a later cycle. `outcome: accumulating` means the available sale is below threshold; `swap_cap_below_sale_minimum` means the raw cap limits the proposed sale below threshold while more tokens remain (review the cap instead of bypassing it). Missing/stale prices produce `valuation_unavailable` and no sale; the next five-minute cycle still collects new tax and retries valuation. Pending signed sales are always reconciled under their existing signatures before preparing anything else. Existing pending operations from a prior worker version are not discarded when adopting the new threshold.

The program credits received quote once: 75% net holder budget and 25% platform budget, with cumulative integer rounding. The collector does not calculate or subtract that fee again, open holder payout rounds, pay the fee wallet, buy back tokens, or burn tokens. Distribution timing is a separate concern. New tax generated by a sale is left for a later cycle, avoiding an endless collect/sell loop.

Empty cycles send no transaction. Safe execution takes priority over timing: RPC outages, graduation, a bad quote, missing verification, low operator SOL, or a pause delay completion. The UI should expose `nextDueAt`, `startedAt`, `completedAt`, `phase`, `outcome`, `saleValuation`, `pending.signature` and `issue`; five minutes is the attempt schedule, not a confirmation guarantee. `completedAt` means the cycle finished its checks, not necessarily that a sale occurred; only finalized sale receipts count as sales. An overdue active cycle resumes before a new cycle starts; several missed slots become one catch-up cycle. Clock rollback cannot repeat an already-started slot.

## Host and adapter contract

Use Node 24.22.1 or compatible Node 24 with `node:sqlite`. Open one `CollectorStore` at a durable path outside Git, bind it to the exact program ID, and retain its journal across restarts. Run exactly one collector process for that deployment, enforced by an OS lock such as `flock` held for its entire lifetime. The in-process busy set only prevents overlapping ticks in that process; it is not a distributed lock. Do not clear/replace the journal to resolve an uncertain transaction.

Construct `Collector` with `enabled: false` by default and an explicit positive raw swap cap no greater than the current on-chain cap. Register only program-owned, validated launch PDAs; discover from finalized chain state, not an untrusted client-supplied list. Call `tick(mint)` promptly (for example once per second) for each registered CA with bounded concurrency. One blocked CA need not block others. Do not run the old shared-signer collector for these mints.

The mandatory adapter methods are:

| Method | Required behavior |
| --- | --- |
| `ready()` | Fail closed unless the reviewed program is deployed and publicly verified, its current binary and retained upgrade authority match the pinned release, config is unpaused, the operator/platform/tax authority/pair bindings are correct, and the operator has the configured SOL reserve. Recheck before broadcast. Never use holder funds for gas. |
| `snapshot(mint, minContextSlot)` | Return `{ sources, mintWithheld }` from a complete finalized same-mint Token-2022 account scan at or above the supplied slot. Include only accounts with positive withheld tax; include the mint's withheld amount separately. Validate tax configuration and canonical vault ownership. Do not silently truncate an RPC scan. |
| `baseBalance(mint, minContextSlot)` | Return the spendable raw base-vault balance from finalized state at or above the last receipt slot, excluding withheld tax. |
| `quoteSale(request)` | Quote the exact capped `request.amount` of this CA via its approved LaunchLab/CPMM pair and value the slippage-protected output using a trusted fresh USD price. Return JSON-serializable `{ mint, amount, quoteMint, minOut, minOutUsdMicros, quotedAt, priceAt, ...routeData }`. Raw amounts and USD micros must be unsigned decimal strings; timestamps are integer Unix milliseconds recording the actual quote/price observation, not refreshed timestamps on cached data. Bind the quote mint to finalized launch state and respect `minContextSlot`. Reject missing/untrusted/manipulable prices, untradeable pools, unsupported quotes and zero outputs. |
| `prepare(request)` | Build/simulate/sign **without broadcasting**. For collection use `client.collect`; for a sale consume the exact checked `request.quote` and wrap it with `client.convert` for this CA's pair and vaults. Bind exact raw amount, minimum output, explicit slippage limit, short deadline, and the current swap cap. Include the unique `request.id` in a Memo instruction so distinct operations cannot accidentally have identical signed messages when sharing a blockhash. Do not silently replace the quote with a different value or route. Return exact signed `wire`, `signature`, message hash, last valid block height and settlement expectations. Never substitute a SOL route or shared wallet. |
| `broadcast(operation)` | Send only the stored signed bytes, checking the configured fee/compute budget. A send timeout is ambiguous, not authorization to create another signature. |
| `reconcile(operation)` | Verify signature history and finalized transaction message hash, success, expected vault deltas, mint/pair and amount. Return `{ status: 'finalized', slot, ...receipt }` only after all checks. Return `{ status: 'pending', rebroadcast: boolean }` while unsettled; permit rebroadcast only of the original still-valid bytes. Return `{ status: 'review', reason }` for failure or unverifiable expired history. Never assume missing history means no execution. |

The engine journals the signed operation before broadcast, keeps one pending operation per CA, and atomically archives its receipt while advancing the phase. A finalized receipt is the only path to the next batch/sale. The supplied RPC adapter checks exact signed-message hashes, signature, mint/owner/decimals, exact base debit, minimum paired credit and gas-only operator debit. An expired signature with unavailable history stays in review; use an archival RPC without discarding the journal. Readiness rechecks the current deployed binary and authority before broadcasts, so a program upgrade pauses new work until the reviewed release pins are updated. A 30-second cache only covers the public verification service response, not the fetched deployed bytes.

## Canary runner

`config.example.json` is a template, not an activation configuration. Copy it to a private directory outside Git; use mode 0600 and an owner-only directory. Substitute the reviewed program ID, verified public commit, exact Docker artifact, RPC endpoint and existing operator key path. A dedicated Jupiter price API key is required by this runner so its request pacing can be managed separately from the existing backend's shared price cache. Do not paste key material or API keys into chat. The defaults describe 1% slippage, a 1M-CU limit, a 25,000-lamport transaction-fee cap and a 0.005-SOL minimum remaining operator reserve; review these and the raw swap cap before running. There is no tip or external transaction transport in this version.

`prices.cjs` uses Jupiter V3's quote-mint entry and its actual price-observation block time. A newly fetched response does not make an old price fresh. Both the observation and route quote must meet the 30-second policy; quiet/unsupported pairs can therefore remain accumulating even above an estimated website dollar value. No stablecoin is treated as a hard $1 peg. LaunchLab and CPMM route quotes are calculated from RPC pool state with the locked Raydium SDK and the base mint's active transfer fee. The resulting exact quote is bound to the signed sale; user-supplied quote JSON is not accepted.

Once deployment, verification, platform configuration and the canary launch are complete, the read-only check is:

```bash
node worker/run.cjs /root/.config/moonz-fusion/collector.json --check
```

This check does not make the full platform ready and does not start a daemon. It validates the program, configuration, operator reserve and explicit mint bindings without opening a key. The release operator must also validate pricing and review the first signed/settled canary receipts. The runner has no all-token enable flag: only explicit `canaryMints` are processed. Do not replace the canary list with a larger deployment until website launch and holder/platform payout reconciliation are connected and reviewed.

For an authorized live canary with `live: true`, invoke `bash worker/run.sh /absolute/private-config.json`. The wrapper holds `flock` on the journal's lock file through process execution. Run one instance (PM2 fork mode if used); never cluster it or clear the journal to work around a lock. A persistent `collector_health` row supplies a timestamp and review-mint list; monitoring must check heartbeat age rather than trust an old `active` value. SIGTERM stops preparing/broadcasting new operations; persisted pending transactions are reconciled at the next start. Never rotate the operator or remove a mint from the canary while its signatures remain unresolved.

Local tests exercise the production adapter against the compiled Fusion and Raydium programs with a simulated RPC transport and deterministic USD price. They cover actual signing/simulation, withheld tax, quote-bound sales, lost send responses, restarted reconciliation, pause and binary-change gates. Price-provider, receipt-corruption and missing-history tests are separate. Real-provider outage behavior, actual privileged graduation, service monitoring and the live canary remain unvalidated.
